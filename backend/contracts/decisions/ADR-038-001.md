# ADR-038-001: reconcile the MAD integration baseline

Date recorded: 2026-10-21. Status: **recorded existing implementation and proposed
resolutions; cross-team/supervisor acceptance pending**. This is a new decision
record created during DDP-038, not a retroactive approval or an earlier ADR.

## Context

SDS6.1 assumes a central Auth service and bcrypt12 password storage; SDS6.2.1
allows partial Kitchen Manager MAD access without a route list. The user selected
independent subsystem logins and a routing-only gateway. Current MAD issues its
own manager JWTs, provisions staff with bcrypt12 but uses scrypt for managers,
and denies non-manager dashboard sessions. SRS/SDS timing and CI triggers also
differ. Source data now mixes unprefixed shared tables and service-prefixed tables.
These are material contract differences, not reasons to invent acceptance.

## Existing local decisions retained for this review

Keep the user-directed independent login/routing architecture, current database
object names, eight-hour manager sessions, manual schema administration and
strict manager authorization. Preserve approved completed-payment/check-in-date
analytics and field-level complaint write exception. No UI, hash migration,
access expansion, broker contract or schema alteration is performed by DDP-038.

## Proposals for explicit adoption

Review the least-privilege Kitchen Manager subset and scoped session/socket
mechanism before implementation. Review integer1..10 task-limit bounds/default3,
active-state cohort and atomic WKMS enforcement. Prefer the stricter one-second
healthy-path UI timing target; agree workload/measurement before claiming it.
Retain earlier full CI checks on pushes/develop/main PRs; implement actual staged
deployment/manual production approval only through a separately reviewed workflow.

Hash compliance requires choosing an approved manager hash migration/verifier
plan or explicit permitted deviation; do not relabel scrypt as bcrypt. Shared
complaint/staff writers must agree lock/version/ownership semantics. Actual
provider event/outbox/ack agreements and source grants must be signed off.

## Consequences

Code can be maintained against a clear current baseline, but existing fixtures
and defaults do not certify other subsystems. Do not share manager signing keys
for convenience, grant KM all MAD channels, change shared tables automatically,
or infer refund/capacity history. Rejected proposals require revised contracts,
compatibility/migration plans and affected tests before rollout.
