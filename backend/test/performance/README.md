## Proposed reproducible profile

| Item                        | Profile `DDP-047-read-v1`                                                                                                         |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Baseline                    | 100 distinct manager test users, one active session/socket each                                                                   |
| Capacity                    | 300 distinct manager test users, one active session/socket each                                                                   |
| Setup                       | Socket clients connected sequentially with 50ms spacing; excluded from steady-state request timing                                |
| Warm-up / measured duration | 5 minutes / 15 minutes per run, same dataset and topology                                                                         |
| Offered API rate            | One request/user/second: 100 or 300 requests/second                                                                               |
| Mixed workload              | Equal cyclic distribution across the 13 read routes in `run.ts`; each user starts at a different route                            |
| Request timing              | Client monotonic clock, request start through full response body/JSON parsing; no redirects or retries                            |
| AC1                         | At least 95% complete within 500ms (nearest-rank p95 <=500ms); failed/time-out requests cannot pass the error gate                |
| AC3 proposed no degradation | Capacity p95 <=110% of 100-user p95, both API gates pass, zero unexpected request errors/disconnects, no skipped offered requests |
| Timeout                     | 5 seconds/request; overrun slots are recorded, never hidden by reducing the target rate                                           |
| Socket behavior             | Actual one-use ticket and allowed Origin, websocket-only; no silent auto-reconnect in healthy capacity run                        |
| Source activity             | Owners must agree and record event rates, order rates and data volumes before acceptance; not generated by this runner            |

The 13 routes cover analytics (overview, bookings/day, revenue/month, food/day,
service requests/week, worker performance/month), kitchen, rooms, tasks,
notifications, staff, complaints and promotions. This deliberately read-only
profile does not generate owner mutations, credential emails, exports or login
bursts. Approve its representativeness or revise/version it before measuring;
never call it the agreed production mix until owners sign. Concurrent sockets
exercise server authorization/fan-out; these are protocol users, not 300 rendered
browsers. Owner review must approve a separate real-browser cohort and account
for any added clients in the final concurrency total.

Runs take about 20 minutes plus setup. Watch API/DB/broker/load-generator metrics
throughout; abort with Ctrl+C for unsafe saturation. The runner disconnects its
sockets in cleanup and returns nonzero on failed API gates. Setup failure returns
nonzero without a completed summary; record it as FAIL, not as a discarded run.
Cancelled measured runs cannot pass. Warm-up disconnects also fail the run.
Use a unique label each time; existing result directories are never overwritten.

Ignored `performance-results/<label>/summary.json` contains counts, per-route
p95/p99, aggregate p50/p95/p99/max, errors, missed slots and gate outcome.
`receipts.json` contains only event ID/type, numeric client ID and receipt time,
not event payloads, tokens or cookies. Correlation data still belongs in the
restricted evidence store. The million-receipt cap fails the gate if exceeded.
The runner does not export full HTTP bodies or error objects containing secrets.

## AC2: committed event through visible update

Agree the DDP-038 timing resolution before acceptance. Current proposal is the
stricter **source-commit to visible UI <=1000ms**; the alternative SRS UI bound is
2000ms, while event propagation must remain <=1000ms. The evaluator requires an
explicit `PERF_UI_BUDGET_MS` of 1000 or 2000; selecting 2000 is not owner approval
to override SDS. The proposed gate checks every complete observation, not only
p95. A 30-second recovery poll cannot satisfy healthy-path latency.

For real KMS, FDS, WKMS and promotion flows, owners commit uniquely correlated
source changes during steady-state load. Collect the DB-confirmed commit time,
broker/MAD receipt timings and corresponding browser-visible update (browser
trace plus assertion of the rendered state after snapshot reconciliation).
Use the real provider commit acknowledgement/audited trace, not event creation
time. Confirm all required clients receive every expected event. Source mutations
remain in their owning service; do not inject fake broker messages as acceptance.

`receipts.json` is evidence of protocol receipt only. It cannot populate
`visibleAt`. Keep the full protocol-client receipt completeness check separately
in the register, and record a reviewed real-browser cohort with both received and
visible observations. Convert correlated, clock-corrected observations to this
JSON schema in a private timing evidence file (numbers are epoch milliseconds):

```json
{
  "expectedClientIds": ["browser-a", "browser-b"],
  "events": [
    {
      "eventId": "actual-source-event-id",
      "committedAt": 1792540800000,
      "receipts": [
        {
          "clientId": "browser-a",
          "receivedAt": 1792540800200,
          "visibleAt": 1792540800700
        },
        {
          "clientId": "browser-b",
          "receivedAt": 1792540800300,
          "visibleAt": 1792540800900
        }
      ]
    }
  ]
}
```

The example is illustrative, never execution evidence. Include ALL expected
committed events, including missing deliveries; never construct the ledger only
from successfully received events. Missing/duplicate clients, duplicate event IDs,
empty data, negative/non-finite intervals, inverted render times or budget breaches
fail evaluation. Preserve original timestamps and clock corrections for review.
